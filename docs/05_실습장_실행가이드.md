# 05. 실습장 PC 실행 가이드 (Docker, 16 CPU, RTX 2080 ×2)

> 학습과 본 실험 평가는 이 문서대로 실습장 PC에서 돌립니다. 노트북에서는 짧은 동작 확인만 합니다.
> 별도의 예산 파일럿 없이 **바로 본 학습**을 시작하고, 처음 1~2시간 동안 학습이 되는지 확인합니다(사용자 결정, 2026-11-11).

## 0. 전체 흐름

| 단계 | 하는 일 | 시간 |
|---|---|---|
| 1 | 준비: 드라이버, Docker, 이미지 빌드, GPU 확인 | 30분 |
| 2 | 동작 확인: 아주 짧은 학습 1회 | 5분 |
| 3 | **본 학습 시작**: 6 k × 5 seed = 30개, 실험당 1,000만 스텝, 끝나면 평가까지 자동 | 속도에 따라 (아래 계산) |
| 4 | **초반 점검**: 10분 뒤 속도, 1~2시간 뒤 학습 여부 확인 → 계속 또는 중단 | |
| 5 | (선택) 성형 없는 대조 1개 — 논문 부록용 | |
| 6 | 결과 가져오기 | |

## 1. 준비 (처음 한 번)

필요한 것: NVIDIA 드라이버 **525 이상**(CUDA 12.1), Docker Engine, Docker Compose v2, NVIDIA Container Toolkit.

```bash
nvidia-smi                                   # 드라이버 버전과 2080 두 장이 보이는지
docker compose version                       # v2 인지 (docker-compose v1 은 GPU 설정을 못 읽음)
docker run --rm --gpus all nvidia/cuda:12.1.0-base-ubuntu22.04 nvidia-smi   # 컨테이너에서 GPU가 보이는지
```

코드 가져오기와 빌드:
```bash
git clone <저장소 URL> ooda && cd ooda      # 이미 있으면: git pull
docker compose build
docker compose run --rm ooda
```
마지막 명령의 출력에 `cuda True | gpus 2 ['NVIDIA GeForce RTX 2080', ...]`가 보이면 준비 완료입니다.

- `ooda/`, `scripts/` 폴더는 컨테이너에 볼륨으로 연결돼 있습니다. 그래서 **코드만 바뀌었을 때는 `git pull`만 하면 되고 다시 빌드하지 않아도** 됩니다. `requirements.txt`나 `Dockerfile`이 바뀌었을 때만 `docker compose build`를 다시 합니다.

## 2. 동작 확인 (5분)

```bash
docker compose run --rm ooda python scripts/train.py --k 1 --seed 0 --timesteps 20000 \
    --n-envs 3 --device cuda --eval-every 10000 --eval-n 20 --out-root results/rl/smoke
```
`[valid] ...`가 두 번 찍히고 `[done]`으로 끝나면 정상입니다. 확인 후 `results/rl/smoke`는 지워도 됩니다.

## 3. 본 학습 시작

```bash
docker compose up -d train            # 백그라운드로 시작 (터미널을 닫아도 계속 돎)
docker compose logs -f train          # 진행 상황 ([시작]/[완료]/[실패]) — Ctrl+C 는 로그 보기만 종료
```

- **실행 순서**: k=1의 seed 0~4부터 시작합니다. 처음 동시에 도는 4개(k1_s0~k1_s3)가 모두 k=1이라, 이것이 파일럿 역할을 합니다.
- **예산**: 실험당 1,000만 스텝(`docker-compose.yml`의 `--timesteps`). 넉넉하게 잡은 값입니다. 25만 스텝마다 검증 승률이 가장 높은 모델을 `model_best.zip`으로 저장하고 평가에는 그 모델을 쓰므로, 예산이 넘쳐도 결과는 손해가 없고 시간만 더 듭니다. 반대로 부족하면 처음부터 다시 돌려야 합니다(이어서 학습하는 기능은 없음).
- **자원 배분**(기본값): 동시 4개 실험 × 실험당 환경 3개입니다. 환경 프로세스 12개와 학습 본체 4개가 CPU 16개를 쓰고, GPU는 실험 2개씩 나눠 씁니다.

## 4. 초반 점검 (중요)

### 10분 뒤: 속도 → 총 소요 시간
```bash
tail -n 3 results/rl/runs/k1_s0/progress.csv | cut -d, -f1-6
```
`time/fps` 열이 실험 1개의 초당 학습 스텝입니다.
**총 소요 시간 ≈ 30 × 10,000,000 ÷ (4 × fps)초.** 예: fps 1,500이면 약 14시간, fps 800이면 약 26시간.
너무 길면 멈추고(`docker compose stop train`) `docker-compose.yml`의 `--timesteps`를 줄인 뒤 다시 시작합니다. 아직 끝난 실험이 없으므로 손해는 그때까지의 시간뿐입니다.

### 1~2시간 뒤: 학습이 되는가
```bash
cat results/rl/runs/k1_s0/eval.csv          # 25만 스텝마다 검증 승률 (mixture = 세 유형 평균)
grep valid results/rl/runs/k1_s*/train.log | tail -n 12
```

| 상황 (k=1 기준) | 판단 |
|---|---|
| 검증 승률(`mixture`)이 꾸준히 오르고 있음 | 그대로 둡니다 |
| 100만 스텝이 지났는데 0.05 근처에서 평평 | `docker compose stop train`으로 멈추고, `eval.csv`·`progress.csv`를 가져와 Claude와 상의 |
| seed마다 크게 다름(어떤 건 오르고 어떤 건 0) | 그대로 두되 기록해 둡니다(학습 불안정성 → 논문 한계 또는 하이퍼파라미터 재검토) |

참고: FSM의 k=1 혼합 승률은 약 0.50입니다. RL이 학습 중 이 수준에 가까워지는지가 H1을 판단하는 첫 신호입니다.

### 그 뒤
- 상태 확인: `docker compose logs --tail 20 train`, `nvidia-smi`
- **중단**: `docker compose stop train`
- **재개**: `docker compose up -d train`. `model_final.zip`이 있는 실험은 건너뛰고, 중단된 실험은 처음부터 다시 합니다.
- 30개가 모두 끝나면 평가(조건당 3,000판, 평가 seed 5,000,000번대)가 자동으로 이어집니다. 평가만 다시 하려면:
  ```bash
  docker compose run --rm ooda python scripts/evaluate.py --workers 15
  ```

## 5. (선택) 성형 없는 대조 — 논문 부록용

보상 성형(`docs/02` 결정 13)이 필요했다는 근거를 남기기 위해, 성형을 끈 k=1 학습 1개를 돌립니다. 본 학습과 무관하므로 **본 학습이 끝난 뒤** 돌립니다.
```bash
docker compose run --rm ooda python scripts/run_experiments.py --ks 1 --seeds 0 --parallel 1 --n-envs 12 \
    --gpus 0 --runs results/rl/noshaping -- --shaping-coef 0
```
비교: `results/rl/noshaping/k1_s0/eval.csv` vs `results/rl/runs/k1_s0/eval.csv`

## 6. 결과 가져오기

| 경로 | 내용 | git |
|---|---|---|
| `results/rl/eval/summary.txt` | 에이전트(FSM, RL-A, RL-B) × k × 유형 승률, 학습 seed별 승률 | 포함 |
| `results/rl/eval/k_curve.png` | 유형별 k 곡선(점선은 FSM k=1 기준선 → k\*) | 포함 |
| `results/rl/eval/summary_ci.csv`, `eval_episodes.csv` | 분석용 원자료 (판 단위) | 제외 → 직접 복사 |
| `results/rl/runs/*/eval.csv`, `progress.csv` | 학습 곡선 | 제외 → 직접 복사 |
| `results/rl/runs/*/model_best.zip` | 학습된 모델 (행동 분석에 필요) | 제외 → 직접 복사 |

`results/` 폴더를 통째로 USB나 `scp`로 노트북에 옮기는 것이 가장 간단합니다. 컨테이너는 root로 파일을 쓰기 때문에, 호스트에서 권한 문제가 생기면 `sudo chown -R $USER results`를 실행합니다.

## 문제 해결

| 증상 | 확인할 것 |
|---|---|
| `cuda False` 또는 `could not select device driver` | NVIDIA Container Toolkit 설치 후 `sudo systemctl restart docker` |
| `docker-compose` 명령에서 GPU 설정 오류 | v1입니다. `docker compose`(v2)를 사용 |
| `CUDA error: no kernel image` | 드라이버가 오래됨(525 미만) → 드라이버 업데이트 |
| `Bus error` / 공유메모리 오류 | `docker-compose.yml`의 `shm_size` 증가 |
| 특정 실험 `[실패]` | `results/rl/runs/<이름>/train.log` 마지막 줄 확인 후 `docker compose up -d train`으로 재실행(실패한 것만 다시 돎) |
| GPU 메모리 부족 | `docker-compose.yml`에서 `--parallel`을 줄임 |

## 참고: 구성 요소

| 파일 | 역할 |
|---|---|
| `ooda/obs.py` | RL 관측 생성(8채널 20×20 격자 + 스칼라 5개). 학습과 평가가 공유 |
| `ooda/gym_env.py` | 추격자 시점 gymnasium 환경. FSM 실행기와 같은 `Episode.advance`를 써서 규칙이 완전히 같음(검증: 180판 일치). 보상 성형 포함 |
| `ooda/rl_policy.py` | CNN 특징 추출기, 학습된 모델을 FSM과 같은 인터페이스로 감싼 `RLPursuer` |
| `scripts/train.py` | 실험 1개 학습, 검증 승률로 최고 모델 저장 |
| `scripts/run_experiments.py` | 실험 여러 개를 GPU에 배정해 동시 실행, 끝난 것은 건너뜀 |
| `scripts/evaluate.py` | FSM·RL-A·RL-B를 같은 평가 seed로 평가, 요약표와 그림 |
